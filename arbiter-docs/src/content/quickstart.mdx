# Quick Start

This guide walks you through a complete flow, from creating a project to protecting your first endpoint.

By the end, your backend will be using Arbiter to **control incoming requests in real time**.

---

## Step 1: Create a Project

Go to the Arbiter dashboard and create a new project.

A project represents a single application or service you want to protect.

Examples:

- Auth Service  
- Payment API  
- Public API  

Each project has its own:

- Rules -> how traffic is controlled  
- API keys -> how your backend connects  
- Analytics -> how traffic is monitored  

---

## Step 2: Generate an API Key

Inside your project, generate an API key.

This key is required by the SDK to:

- Identify your project  
- Fetch rule configuration  
- Send analytics events  

Store it securely:

```env
ARBITER_API_KEY=arb_live_xxx
```

---

## Step 3: Create a Rule

Define a rule in the dashboard.

Example:

- Rule name: `login`  
- Limit: `5`  
- Window: `10 seconds`  

This means:

> A single client can make at most 5 requests within 10 seconds.

After that, requests will be blocked until the window resets.

---

## Step 4: Initialize Arbiter

Install the SDK:

```bash
npm install arbiter-sdk
```

Initialize it in your backend:

```ts
import { createArbiterClient } from "arbiter-sdk";

const arbiter = createArbiterClient({
  apiKey: process.env.ARBITER_API_KEY as string
});

await arbiter.init();
```

### What `init()` does

- Validates API key  
- Fetches project configuration  
- Caches rules locally  
- Prepares request validation pipeline  

This step ensures low-latency decisions during runtime.

---

## Step 5: Protect an Endpoint

Use `arbiter.protect()` inside your route:

```ts
app.post("/login", async (req, res) => {
  const result = await arbiter.protect({
    key: req.ip,
    rule: "login"
  });

  if (!result.allowed) {
    return res.status(429).json({
      message: "Too many requests",
      decision: result
    });
  }

  // Continue normal logic
});
```

---

## Request Input

```ts
type ProtectInput = {
  key: string;   // unique identifier (IP, userId, token)
  rule: string;  // rule name defined in dashboard
};
```

---

## Response Format

```ts
type ProtectResponse = {
  allowed: boolean;
  remaining: number;
  resetIn: number;   // seconds
  reason?: string;
};
```

Example:

```json
{
  "allowed": false,
  "remaining": 0,
  "resetIn": 6,
  "reason": "rate_limit_exceeded"
}
```

---

## What is `key`?

The `key` determines **who is being rate limited**.

Common choices:

- `req.ip` -> per IP limiting  
- `user.id` -> per user limiting  
- `apiKey` -> per client/application  

### Important

- Use a **stable identifier**  
- Do not use random or changing values  
- Incorrect keys lead to incorrect rate limiting  

---

## What Happens Internally?

When a request is processed:

1. SDK checks cached rule configuration  
2. Sends validation request to Arbiter service  
3. Service updates counters in Redis  
4. Rule is evaluated  
5. Decision is returned (ALLOW / BLOCK)  
6. SDK returns result  
7. Analytics event is recorded  

This flow is optimized for low latency and consistency across distributed systems.

---

## Testing Your Setup

Send multiple requests quickly to your endpoint:

- First few -> allowed  
- After limit -> blocked (HTTP 429)  

This confirms your rule is working correctly.

---

## Common Mistakes

- Not calling `init()` before using `protect()`  
- Using unstable keys (e.g. random values)  
- Rule name mismatch between dashboard and code  
- Exposing API key on frontend
